# Защо stripe-node увисва след повторен опит

Скриптът ви прави едно нещо: взима клиент от Stripe, отпечатва го, излиза. Отпечатва клиента. И после просто… стои. Без грешка. Без висящ promise. Курсорът мига 80 секунди и чак тогава получавате обратно командния ред.

Пускате го отново — излиза веднага. Трети път — 80 секунди. Не сте променили и ред.

Това е бъгът, докладван в хранилището на stripe-node на 15 октомври 2026 г., а шест дни по-късно — и от втори човек. Работата е свършена. Нещо в SDK-то отказва да остави Node процеса да умре, а спусъкът е последното, което бихте заподозрели: повторен опит, който *е успял*.

Ето какво е интересното: този бъг е роден от поправка. През август Stripe затвори по-неприятен проблем, при който същият timeout изобщо не работеше.

## Проблемът

Докладващият, `KevinDeLaTorre`, го казва ясно в [issue #2897 на stripe-node](https://github.com/stripe/stripe-node/issues/2897): *"От 22.6.0 повторен опит оставя таймера на `timeout` от неуспешния опит въоръжен. Заявката успява, но с подразбирания timeout от 80 s кратко живеещ процес остава жив 80 секунди, след като работата му е приключила."*

Малко контекст. stripe-node е официалната Node.js библиотека на Stripe. Когато заявка се провали с 5xx или 409, SDK-то автоматично я повтаря (`maxNetworkRetries` по подразбиране е 1). Всяка заявка има и `timeout` — 80 000 ms по подразбиране — наложен чрез `setTimeout`, който прекъсва заявката, ако продължи твърде дълго.

Тестовата матрица на докладващия е това, което убеждава: същият скрипт на осем версии на SDK-то. От 18.5.0 до 22.5.0 излизат за милисекунди. От 22.6.0 до 23.1.0-beta.1 оставят един таймер и чакат целия timeout. Контролен тест без 500 излиза чисто навсякъде.

Шест дни по-късно `hnoble5` подаде [#2908](https://github.com/stripe/stripe-node/issues/2908) от различна среда (код за Cloudflare Workers под тест) със същия симптом: *"Node процесът остана отворен около 80 секунди, след като тестовете приключиха."*

И двата доклада използват `Stripe.createFetchHttpClient()` — транспорта на SDK-то, базиран на fetch. Запомнете това.

## Дебъг танцът

Първи инстинкт: отворен handle, нещо още слуша. Добавяте `process._getActiveHandles()`. Един `Timeout`. Чий? Node не казва.

Второ предположение: вашият код. Търсите `setTimeout`. Нищо, което не чистите. Свеждате скрипта до една-единствена Stripe заявка. Пак 80 секунди.

Сега числото започва да гложди. 80 секунди е странно конкретно. Задавате `timeout: 5000` на Stripe клиента и увисването пада на 5 секунди. Значи таймерът е request timeout-ът на SDK-то — но заявката *е приключила*. Защо приключила заявка още държи таймер?

Грешният завой, който има смисъл: връщате по една минорна версия назад, докато увисването изчезне. Точно това направи докладващият. Работи — просто струва един следобед. Отговорът е 22.6.0, пусната на 26 август.

В нейния changelog има един ред, който изглежда несвързан: *"correctly throw connection errors if the server drops while sending the HTTP response body"* ([PR #2815](https://github.com/stripe/stripe-node/pull/2815)). Той поправи [issue #2814](https://github.com/stripe/stripe-node/issues/2814): замръзнала връзка можеше да увеси stripe-node завинаги, защото timeout-ът се изчистваше щом пристигнат *хедърите* на отговора и никога не покриваше *тялото*.

Моментът "аха" е четенето на тази поправка. Таймерът вече остава въоръжен след пристигането на хедърите, а който чете тялото, трябва да го освободи:

```ts
// src/net/FetchHttpClient.ts (22.6.0+)
async toJSON(): Promise<any> {
  try {
    text = await this._requestTimeout.guard(this._res.text());
  } finally {
    this._requestTimeout.release();   // единственото място, където таймерът умира
  }
  return this._parseResponseBody(text);
}
```

Сега помислете какво прави пътят за повторен опит в `RequestSender` с един 500: вика `retryRequest(...)` и изхвърля отговора, *без да прочете тялото*. Никой не вика `release()`. `setTimeout` продължава да живее, event loop-ът на Node вижда жив таймер и процесът чака 80 секунди за таймер, който, когато най-сетне се задейства, прекъсва заявка, приключила отдавна.

## Решението

Поправката, [PR #2895](https://github.com/stripe/stripe-node/pull/2895) от `jar-stripe`, излезе в **stripe-node 23.0.1 на 22 октомври 2026 г.** Ако сте на 22.6.0 или по-нова с fetch клиента, обновете:

```bash
npm install stripe@latest   # ≥ 23.0.1
```

Промяната е малка. Отговорите получиха незадължителен метод `dispose()`, а пътят за повторен опит го вика, преди да изхвърли отговора:

```ts
// src/RequestSender.ts (23.0.1)
if (RequestSender._shouldRetry(res, requestRetries, maxRetries)) {
  res.dispose?.();
  return retryRequest(makeRequest, apiVersion, headers, requestRetries + 1);
}
```

```ts
// src/net/FetchHttpClient.ts (23.0.1)
dispose(): void {
  this._requestTimeout.release();
  this._requestTimeout.abort?.();
  const body = this._res.body;
  if (body && typeof body.cancel === 'function' && !body.locked) {
    body.cancel().catch(() => {});
  } else if (body && typeof body.destroy === 'function') {
    body.destroy();
  }
}
```

Защо три стъпки? Изчистването на таймера спира процеса да чака. Прекъсването на контролера казва на fetch, че отговорът е мъртъв. Отмяната на тялото затваря непрочетения поток, за да се върне сокетът в пула. Докладващият потвърди на клона с поправката: нула изтекли таймери, изход за 506 ms.

Какво пропускат новаците: **това засяга само fetch клиента.** Подразбираният `NodeHttpClient` използва `req.setTimeout()` върху самия сокет, така че неговият timeout умира заедно със заявката. Попадате на този бъг, когато изрично изберете `createFetchHttpClient()`.

Ако още не можете да обновите, намалете `timeout` до нещо разумно за вашата работа; това ограничава колко дълго живее таймерът-призрак. Не задавайте `maxNetworkRetries: 0`, за да го избегнете — ще размените козметично увисване за реално провалени плащания.

## Поуката

Всеки ресурс има собственик, а собственикът се сменя, когато се смени пътят в кода. Преди 22.6.0 собственик на таймера беше fetch заявката: хедърите пристигат, таймерът се чисти, готово. Августовската поправка премести собствеността към "който чете тялото". Това беше правилното решение — затвори реално увисване. Но създаде ново правило, а пътят за повторен опит така и не научи за него, защото той не чете тела.

Изводът: когато промяна премества почистването от "автоматично" към "някой трябва да извика X", потърсете всяко място, което изхвърля ресурса, без да извика X — ранни return-и, retry цикли, error клонове. Там таймерите отиват да живеят вечно.

## Често задавани въпроси

### Засяга ли това подразбирания Node HTTP клиент?

Не. И двата доклада използват `Stripe.createFetchHttpClient()`. Подразбираният `NodeHttpClient` прилага timeout-а чрез `req.setTimeout()` върху обекта на заявката и вика `req.destroy()`, когато се задейства, така че таймерът е вързан към сокета и изчезва заедно със заявката. Изложени сте на Deno, Cloudflare Workers или Bun, където fetch клиентът е нормалният избор, или ако сте подали `httpClient: Stripe.createFetchHttpClient()` в Node.

### Кои версии са засегнати и кои го поправят?

Засегнати: от 22.6.0 до 23.0.0, плюс предварителните издания на 23.1.0 преди поправката, при използване на fetch клиента. Регресията дойде с PR #2815 в 22.6.0 (26 август 2026 г.). Поправката е PR #2895, пусната в 23.0.1 на 22 октомври 2026 г. и включена в 23.1.0 и по-нови. Матрицата на докладващия потвърди, че от 18.5.0 до 22.5.0 са чисти — макар тези версии още да имат по-старото увисване при timeout на тялото от #2814.

### Deno тестовете ми падат с изтекъл таймер — същият бъг ли е?

Много вероятно, ако Stripe заявка в този тест е била повторена. Санитайзерът на Deno отказва да пусне тест, който оставя висящ таймер, а точно това прави изхвърлен отговор при повторен опит на 22.6.0–23.0.0. Обновете до 23.0.1 или по-нова и санитайзерът би трябвало да млъкне. Ако още се оплаква, уверете се, че вашият mock fetch връща истински `Response` с тяло, защото поправката работи, като отменя този поток на тялото.
