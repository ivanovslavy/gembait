# Защо Postgres RLS изтича между клиенти

Представете си тикета в поддръжката. Клиент отваря своя регистър на рисковете и вижда три реда, които принадлежат на друга фирма. Не грешка. Просто чужди данни, които стоят там, сякаш винаги са били негови.

Имате включена сигурност на ниво ред — RLS, вграденият начин на Postgres да скрива редове от всеки, който няма право да ги вижда. Всяка заявка задава клиента (tenant) преди да чете. Не можете да го възпроизведете на лаптопа си. Случва се само под натоварване, и то само понякога.

Точно това един разработчик донесе в Stack Overflow през септември: multi-tenant Node приложение върху PostgreSQL 16, библиотеката `pg` (node-postgres), учебникарска RLS политика — и „малък брой заявки връщат редове, принадлежащи на друг tenant“.

Неудобната част: кодът във въпроса е правилен. Изтичането идва от това, което кодът *около* него оставя след себе си върху споделена връзка.

## Проблемът

Политиката е възможно най-простата: покажи ред само когато неговият `tenant_id` съвпада със сесийна променлива, наречена `app.current_tenant`.

```sql
CREATE POLICY tenant_isolation ON risks
  USING (tenant_id = current_setting('app.current_tenant')::uuid);
```

Всяка заявка взема клиент от пула, задава tenant-а, чете и връща клиента обратно:

```js
const client = await pool.connect();
try {
  await client.query("SELECT set_config('app.current_tenant', $1, false)", [tenantId]);
  const rows = await client.query('SELECT * FROM risks');
  return rows.rows;
} finally {
  client.release();
}
```

Очаквано: всяка заявка вижда само своя tenant. Реално: под паралелно натоварване няколко заявки виждат редовете на друг tenant.

Питащият имаше заобиколно решение — `SET LOCAL` в явна транзакция караше изтичането да изчезне. Но по собствените му думи: „Исках да разбера защо първата версия се проваля, вместо просто да превключа.“ Правилен инстинкт.

Не е единичен случай — [„Enforcing row-level security in a shared postgres pool“](https://stackoverflow.com/questions/77272972/enforcing-row-level-security-in-a-shared-postgres-pool) пита същото. Laurenz Albe, core contributor в PostgreSQL, остави ключовия коментар: „Това не може да се случи, ако целият код на заявката се изпълнява в една сесия.“ Тогава — защо не беше така?

## Танцът на дебъгването

Първи инстинкт: политиката е грешна. Пускате я в `psql` като един потребител, един tenant. Перфектна изолация. Не е политиката.

Второ предположение: пулът споделя един клиент между две заявки. Не го прави — `pool.connect()` ви дава клиент, който никой друг не може да пипне, докато не извикате `release()`.

Досега load тестът е минал четиридесет пъти и е изтекъл в шест от тях. Stack Overflow е отворен в осем таба. Един таб предлага отделна връзка за всеки tenant. Питащият го пробва: работи, докато не станат няколко десетки tenant-а. Задънена улица.

И тогава идва мисълта, от която стомахът ви се свива. Postgres връзката не е тръба. Тя е *сесия*, а сесията има памет. `SET` (както и `set_config(..., false)`) е със сесиен обхват — документацията казва, че стойността „остава до края на сесията, освен ако не бъде презаписана от друг SET“. Пулът никога не приключва сесията, когато освободите клиент. Той подава същата сесия, все още носеща последния tenant, на следващия.

Така че изолацията се пази само ако **всяко изявление**, което докосва `risks`, тече върху връзка, чийто tenant е зададен *в същата заявка*. Нарушете това веднъж, където и да е, и наследявате чужд tenant.

Приетият отговор, от Zegarek, изброява къде обикновено се крие това „веднъж, където и да е“:

- Някъде `pool.query()` вместо `client.query()`. Всяко извикване „е свободно да попадне в съвсем различна сесия, с друг зададен tenant“.
- `SET LOCAL` извън транзакция. Postgres предупреждава `SET LOCAL can only be used in transaction blocks` — и после не прави нищо.
- Единица работа, която изобщо не задава tenant, и затова пази „каквото някой друг worker ѝ е оставил“.
- Втори пул под вашия — PgBouncer в transaction режим, pgpool-II — който сменя backend връзката по средата на заявката.
- Стойност по подразбиране за `app.current_tenant`, зададена чрез `ALTER DATABASE` или `ALTER ROLE`, която се връща след всеки `RESET ALL`.

## Решението

Три слоя.

**1. Ограничете tenant-а до транзакция, не до сесия.** `true` в `set_config` означава „локално“, същото като `SET LOCAL`. Ефектът трае „само до края на текущата транзакция, независимо дали е потвърдена или не“. Дори следващата заявка да забрави да зададе tenant, тя не наследява нищо.

```js
export async function withTenant(tenantId, fn) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    await client.query("SELECT set_config('app.current_tenant', $1, true)", [tenantId]);
    const result = await fn(client);   // every query uses *this* client
    await client.query('COMMIT');
    return result;
  } catch (err) {
    await client.query('ROLLBACK').catch(() => {});
    throw err;
  } finally {
    client.release();
  }
}
```

Помощникът премахва и изкушението за `pool.query()`: извикващите получават `client`, не пула. При PgBouncer в transaction режим явният `BEGIN … COMMIT` е и това, което закотвя изявленията ви към един backend.

**2. Нулирайте сесията на връщане.** За да хванете остатъчно състояние от по-стари пътища в кода, почистете връзката при събитието `release` на `pg-pool`:

```js
pool.on('release', (err, client) => {
  if (!err) client.query('ROLLBACK; RESET ALL; UNLISTEN *; SELECT pg_advisory_unlock_all();')
    .catch(() => client.release(true)); // destroy on failure
});
```

Защо не `DISCARD ALL`? Работи, но както Franck Pachot отбелязва в коментарите, той изхвърля и кешираните планове и кеша на секвенциите, а и не може да тече в транзакционен блок. `RESET ALL` е частта, която чисти параметрите.

**3. Проваляйте се затворено.** Подайте `true` като втори аргумент на `current_setting()`, така че липсващ tenant да върне `NULL` — а `tenant_id = NULL` скрива всеки ред. Никога не давайте стойност по подразбиране на `app.current_tenant`. И проверете като кого се свързвате: собствениците на таблици и суперпотребителите заобикалят RLS, освен ако не направите `ALTER TABLE risks FORCE ROW LEVEL SECURITY`.

## Поуката

Пулът от връзки ви дава ексклузивна употреба. Не ви дава чист лист. Всяка pooled връзка е сесия с памет, и всичко, което `SET`-нете там, е бележка, оставена за следващия.

Правилото, което следваме в multi-tenant Node и PostgreSQL услугите в GEMBA IT: състоянието на заявката е или ограничено до транзакция, или изрично нулирано — никога нито едното. Сложете го зад един помощник и пуснете паралелен тест, който проверява изолацията между tenant-ите. Изтичане, което се появява „понякога под натоварване“, е бъгът, който еднопотребителски тест никога не намира.

## Често задавани въпроси

### PgBouncer в transaction режим разваля ли това?

Да, освен ако всяко зависимо от tenant-а изявление не тече в една явна транзакция. В transaction pooling режим PgBouncer може да даде на всяко *изявление* различна backend връзка, така че сесийният `SET` попада на един backend, а вашият `SELECT` — на друг. Използвайте помощника `withTenant` (`set_config(..., true)` в `BEGIN … COMMIT`) или превключете PgBouncer в session режим.

### Да пускам ли DISCARD ALL при всяко освобождаване?

Това е най-простото пълно нулиране, но е грубо. Изхвърля prepared statements, кеширани планове и кешове на секвенции, така че всяка преизползвана връзка плаща цената за загряване отново — и се проваля в транзакционен блок. По-пестеливото почистване от темата е `ROLLBACK; RESET ALL; UNLISTEN *; SELECT pg_advisory_unlock_all();`. Ако разчитате на prepared statements, преместете `PREPARE` извикванията в хука `onConnect` на пула.

### Защо не мога да напиша SET app.current_tenant = $1?

Оригиналният въпрос използва точно това, но `SET` е utility команда и Postgres замества `$1` placeholder-и само в обикновени изявления — `pg` получава `syntax error at or near "$1"`. Параметризираният еквивалент е `SELECT set_config('app.current_tenant', $1, true)`. Никога не слепвайте tenant-а като низ в `SET`; това е точка за инжектиране, през която се сменят tenant-и.
